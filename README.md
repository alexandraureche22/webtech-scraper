# Website Technologies Scraper
## Solution Explanation
### Manual exploration

I opened one of the domains from the list and looked through View Page Source for technologies I could think of right away. To start, I found 4 (Salesforce Commerce Cloud, Adobe Experience Platform Launch, Google reCAPTCHA via google.com/recaptcha, Salesforce CQuotient via cdn.cquotient.com), and figured I'd build a manual dictionary as an exercise, so I'd have an easier time figuring out what to do next.
I put together that list with the 4 technologies, then added 3 more from a different site, just to have something a bit more varied. I thought through how to turn this into code: compare a technology's name against text found in a script, and if it matched, the technology was there. But it was obvious pretty fast that writing hundreds of these by hand wasn't realistic. So this manual list was really just for testing, to understand the process myself, not meant as the actual solution.
After that I looked into how to code this as simply as possible. It was a bit confusing at first, I didn't really know how to pull data from a website and compare it, so I looked things up from a few sources and used some AI help to get it explained in a way I could follow. That's how the first version of the code came together, and I tested it on a single domain, it correctly found the same technologies I'd already spotted by hand. Then I tried 3 domains, but the third came back empty, simply because the dictionary was too small and nothing matched.
### More manual searching
I picked 2-3 random domains from the list and manually checked for a few more technologies on each. On appelpsychotherapy.com I found Wix (`<meta name="generator" content="Wix.com Website Builder"/>`, plus a few more matches). After that it slowed down, I was only checking 7 technologies per site, and it was hard to get hits with such a small list.

### Finding an existing signature database
I looked online for somewhere that already had technology lists written out and ready to use, and found a GitHub repo with files like a.json, b.json, and so on. I grabbed the a.json URL and ran a test search for Shopify. The signatures are split by first letter (a.json, b.json, ..., \_.json), at raw.githubusercontent.com/enthec/webappanalyzer/refs/heads/main/src/technologies/{letter}.json. Each technology can carry several types of signal: cookies, dom, headers, js, meta, scriptSrc, scripts, url, xhr. I started with scriptSrc and meta, since those matched what I'd already found manually and were simpler to implement than DOM selectors or JS variable detection. I then tested a function that downloads and merges all the signature files, which came out to 7628 technologies total.

### First real test, regex error
Testing the detector function on disneystore.com ran into trouble. I hit an error at re.search(), because Wappalyzer's patterns sometimes carry metadata after a semicolon, confidence or version info, and Python was trying to read that as regex too, with the \1 reference causing the failure. Fixed it with a clean_pattern() function that keeps only the regex part before the first semicolon.

### Meta tag false positives
Running the first version on disneystore.com turned up something odd: a bunch of unrelated technologies (Amazon Pay, Moodle, Gitea, TiddlyWiki, nothing to do with a Disney store). The problem was in how I checked meta tags. My code only checked whether the field name ("id", "image", "title", "description") appeared anywhere in the HTML, and those are common enough to show up on almost any page regardless of technology. It was detecting "Amazon Pay" just because the letters "id" turned up somewhere random, not because an actual Amazon Pay meta tag existed.
Fixed it by switching the logic: instead of checking if the text shows up anywhere, I used regex to look specifically for a real `<meta>` tag with the exact name attribute I wanted (`<meta name="generator" content="...">`). That checks actual HTML structure instead of just whether some letters happen to appear somewhere. Felt like an important lesson: "the text appears somewhere" isn't a good enough definition of a match, especially with real data where common words can quietly produce false positives without anyone noticing right away.

### Running on all 200 domains, too slow
Running the script on all 200 domains took something like 3+ hours to load and finish. Not efficient.
So I looked for a way to cut the time down, saving results as I went and making requests in parallel, so while one site is being checked the code is already working on 19 others. That did cut the time, down to around an hour, but a new problem showed up: some sites, abbikadabbisbakingco.com for one, came back with 491-508 technologies, which made no sense given the task itself says only 477 total were found across all 200 domains combined. Pointed to another false-positive issue, similar shape to the meta tag one, just at a different scale.

## Debate Topics
### 1. Main issues with the current implementation

The biggest issue is speed and iteration cost. Running on just 200 domains took hours, first around 3, then about 1 after adding parallel requests. That's a problem beyond the wait itself: if the code has a bug or I missed something, I have to fix it and run the whole thing again, waiting just as long to find out if the new result is right. There's no guarantee the first run gets it correct, so debugging gets expensive in time, not just effort. At real scale this would be much worse, waiting hours or days just to learn something needs fixing isn't sustainable.
Digging into why it was so slow, the bottleneck wasn't the network requests, it was that for every domain, the code looped through all 7628 technologies and recompiled each regex pattern from scratch with re.search(). That's over 1.5 million regex compilations across the full run, which adds up fast. The fix would be precompiling every pattern once at the start with re.compile(), then reusing those compiled patterns for every domain instead of rebuilding them each time.
The second issue is coverage. I only implemented 2 of the 8 signal types Wappalyzer supports, scriptSrc and meta. Not a huge fraction on paper, but a reasonable starting point, it works and catches real, verifiable technologies. Still, I'm almost certainly missing technologies that only show up through cookies, JS variables, HTTP headers, or DOM structure, none of which the current implementation checks.

### 2. Scaling to millions of domains in 1-2 months
The current approach, one machine, some parallel requests, works fine for 200 domains but wouldn't come close to scaling to millions in a reasonable timeframe. Even with more threads on one machine, you're still limited by how much a single computer can handle, and by how many requests one IP can send before sites start rate-limiting or blocking it.
The real fix isn't more threads on one machine, it's spreading the work across many. Split the list into chunks, have each chunk processed by a different machine in parallel, cloud infrastructure makes this practical since you can spin up many workers instead of being stuck with one laptop's processing power.
Not every domain needs the same treatment either. A large, well-known site isn't likely to change its tech stack often, so once checked it doesn't need constant re-crawling. Prioritizing which domains get checked first, and how often they get rechecked, saves a lot of wasted time and requests compared to treating every domain the same on every run.
The precompiled-regex fix matters even more at this scale. At 200 domains the wasted time from recompiling regex every time was annoying. At millions, that same inefficiency multiplied is the difference between finishing in weeks versus months.

### 3. Discovering new technologies in the future
This connects to something I actually ran into manually: on gogroupauto.com I found a script loaded from a domain called launch-darkly, a technology I didn't recognize at first. The name looked specific and unusual, not generic, so I looked it up and found it was LaunchDarkly, a feature-flagging service. That's basically what discovering a new technology comes down to: noticing something that doesn't match anything you already know, and being curious enough to check what it actually is.
To make that systematic instead of eyeballing a handful of sites by hand, I'd have the crawler flag any script src domain that doesn't match a known signature, instead of silently ignoring it. Each unmatched domain gets logged as a candidate rather than thrown away.
The useful part is frequency. An unknown domain on one site out of thousands probably isn't worth chasing, could be something custom. But the same unrecognized domain showing up across many unrelated sites is a strong signal it's an actual widely-used technology that's just missing from the database. Those repeat unknowns are the ones worth investigating manually, the same way I did with LaunchDarkly, and once confirmed they could get added as new signatures. That's also, notably, how the enthec/webappanalyzer database itself grows, I saw open pull requests on their GitHub adding new technologies exactly this way.
